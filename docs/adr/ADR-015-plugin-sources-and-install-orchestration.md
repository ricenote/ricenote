# ADR-015：插件三路来源、统一安装编排与任务队列

- 状态：已接受
- 日期：2026-10-11
- 修订：[ADR-007](ADR-007-plugin-package-install.md)（压缩包上传降级为本地来源的一种入口）

## 背景

ADR-007 把插件安装定为"后台上传 ZIP"一条路。实践下来有三个缺口：

1. **没有版本概念**：升级要靠人工重新打包上传，无法按语义化版本识别可用更新；
2. **依赖无处安放**：插件若依赖 npm 包，只能手动塞进包里（而包里不该有 `node_modules`）；
3. **开发迭代慢**：本地改一行要重新打包、上传、重启。

同时，ADR-007 当年把说明书 §1.2 的"非目标"扩大解释为"不做从 URL 自动下载"。
复核原文后确认：说明书禁止的是**通用主题 SSR 适配器与插件市场支付**，
并没有禁止"从注册表解析并安装"。因此本轮修正口径。

## 决策

### 1. 三种来源，压缩包归入 `local`

| 来源 | 形态 | 依赖与构建 | 更新检查 |
| --- | --- | --- | --- |
| `registry` | npm 包名（可带版本区间，如 `ricenote-nav@^1.2.0`） | 自动装依赖，可执行构建 | 有（对比 semver） |
| `git` | `repo + ref`（tag / 提交 / 分支） | 取源码后按 `scripts.build` 构建 | 有（对比远端提交） |
| `local` | 目录路径，或压缩包（`via: 'zip'`） | 目录按 `package.json` 处理；压缩包不参与版本管理 | 无（明确标注"不可检查"） |

来源元数据落在 `rn_plugins`（`source_type/source_spec/source_ref/resolved_version/integrity/installed_via`），
扩展中心与 CLI 都会展示。**历史记录回填为 `local`**；`installed_via` 留空
（v0.4.0 之前无法区分"上传"与"手工拷贝目录"，与其猜一个值不如留空并在界面标注"历史记录"）。

### 2. 编排三段式，失败必回滚

```
resolve（解析来源到工作区） → prepare（校验清单/装依赖/构建） → commit（换名落盘 + 写来源 + 审计 + 标记待重启）
```

- **不可逆动作压到最后一刻**：网络与磁盘错误都发生在工作区，`commit` 之前不影响现有版本；
- `commit` 顺序：复制到 `<target>.incoming-*` → 旧目录改名为 `<target>.backup-*` →
  incoming 改名转正 → 删除备份。任一步失败即还原备份，**"升级失败导致插件消失"是绝不允许的**；
- **发现机制跳过瞬时目录**（`.incoming-*` / `.backup-*` / 点开头），双保险：
  即使备份清理失败，也不会被当成"同一 ID 的第二个插件来源"；
- 复制时排除 `node_modules`：依赖由 `prepare` 阶段的包管理器安装（结构正确、平台正确），
  从工作区拷来的软链换位置就失效；
- 依赖装在**插件目录内**（`<pluginDir>/node_modules`），落盘后 Node 从模块位置向上查找即命中，
  不需要额外解析机制，也不会污染内核自己的依赖。

### 3. 依赖里带 `workspace:` 协议时跳过安装

单调仓库内的插件（`@ricenote/shared: workspace:*`）无法独立安装，在仓库外 `pnpm install` 必然失败。
编排识别到该协议后**跳过依赖安装并使用其构建产物**，同时提示"该插件声明了构建脚本，
请在其仓库内先构建"。开发这类插件的正确姿势是把它登记到本地开发目录（见决策 5）。

### 4. 任务队列：进程内串行 + 落库 + 轮询日志

`rn_plugin_jobs`（`id/plugin_id/action/source/status/step/progress/log_text/error/actor_id/started_at/finished_at`）
+ 进程内执行器：

- **全局串行**（同一时刻只有一个任务改磁盘）+ 同类任务去重（重复点安装返回 409）；
- 进度与日志落库：后台刷新页面后仍能看到"上次装到哪一步"，CLI 与后台看到的是同一份记录；
- 日志保留末尾 64KB（任务面板看的是最近输出，不需要完整历史）、写入按 600ms 合并；
- 后台以轮询 `GET /plugins/jobs/:id` 获取增量，不用 SSE：跨代理更可靠，收益不成比例。

### 5. 开发期本地目录：改动即自动重启

配置 `RICENOTE_LOCAL_PLUGINS`（逗号分隔）登记本地插件根目录，它们：
- 参与插件发现（与官方目录、第三方安装目录并列）；
- 由进程入口在**开发环境**监视，文件变更 → 抖动合并（900ms）→ 自动重启内核。

本地目录**不需要"安装"这个动作**，因此不存在"改了源码还要重新安装"的问题。

> 为什么是"自动重启"而不是模块级 HMR：Node 的 ESM 模块缓存按 URL 生效，
> 而 `loadPluginModule()` 不做缓存破坏（给 URL 加查询串会让静态导入仍是旧代码，
> 新旧混跑比"没生效"更难排查，见 ADR-012）。因此快速迭代只能是重启内核。

### 6. 权限与安全

- 新增权限点 **`plugin.install`**（安装/更新/卸载/构建），默认仅 `administrator` 具备；
  `plugin.manage` 保留给启停与设置。理由：安装会在服务器上执行插件代码，
  风险等级与"启用一个已存在的插件"完全不同；
- **安装第三方插件等同授予其服务器代码执行权限**（用户决策：允许依赖安装脚本与构建脚本）。
  后台必须以高风险确认框明示、需要勾选后才可提交，并写入审计（含 `allowScripts` 选择）；
- Git 地址走**白名单**（`https://` / `ssh://` / `git@host:path`）：
  拒绝 `ext::`（git 的传输助手等于远程执行命令）、`file://` 与本地路径（否则服务器会去读任意本地仓库）；
- npm 包做 **sha512 完整性校验**（`dist.integrity`），不一致立即中止；
- 私有源地址与令牌**只从环境变量读取**（`RICENOTE_NPM_REGISTRY` / `RICENOTE_NPM_TOKEN`），
  不落库、不进日志；
- 落盘前有整树体积上限；解包仍走 zip-guard 两阶段校验。

### 7. 与既有决策的口径修订

- **ADR-007 决策 4**（扩展名白名单仅 `.js .mjs .cjs .json .sql .md .txt .map`、不含 `.css`）
  与"插件自带后台界面"冲突，已放宽：新增 `.css/.html/.wasm` 与字体图片类型，
  **仍禁止 `.node`**（无法跨平台分发且加载无检查，与"安装即可见"的审计目标冲突）；
  体积上限从 16MB/64MB 调整为 32MB/96MB；
- **说明书 §1.2 非目标**口径改回原文：只禁止"通用主题 SSR 适配器"与"插件市场与支付"，
  从注册表解析安装属正常能力；
- **ZIP 上传保留**（离线兜底），但语义降级为 `local` 来源的一种入口形式。

## 后果

- 升级变成"点一下"：扩展中心显示"可更新 v1.3.0"与行内更新按钮；CLI 同样有 `plugin updates`；
- 安装过程可观测：步骤条 + 等宽日志面板，失败原因直接可读（`--no-audit` 这类参数错误
  不会再表现为一个语焉不详的 500 —— 这是实测中真实踩到的坑）；
- 代价：Core 新增 `tar` 依赖与外部命令调用（包管理器、git），安装能力受运行环境
  （是否有 pnpm/npm/git、能否访问 registry）影响，因此工具链探测失败时会给出
  "缺什么、怎么装"的可操作错误，而不是抛 ENOENT。

## 被否决的方案

- **让插件作者自带打包好的 `node_modules`**：包体积膨胀、跨平台二进制不兼容、
  与"扩展名白名单"直接冲突；
- **用 git 直接拉 npm tarball**（或反之）：两者语义不同（一个要构建、一个已构建），
  合并成一条路会让"要不要跑构建"变成猜；
- **沙箱化安装脚本**（禁用 `postinstall`）：会破坏大量正常包；既然"安装即授予代码执行权限"
  已是明确口径，就用**高风险确认 + 审计 + 默认仅管理员**来承担责任，而不是假装安全。
