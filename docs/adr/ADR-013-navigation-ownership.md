# ADR-013：顶部导航栏由独立插件 `rice.navigation` 拥有，导航项只引用内容 ID

## 状态

已接受（v0.3.0 后续变更，与 ADR-010 一同划清"内容"与"站点结构"的边界）。

## 背景

`ADR-010` 引入独立页面后，`rice.pages` 顺手在 `header.navigation` 插槽里输出了已发布页面的链接，
理由是"页面应当能被找到"。这在只有页面一个内容来源时成立，但很快暴露三个问题：

1. **同一插槽出现多个写入者**：文章、分类、外链都想进导航栏时，每个插件都会往
   `header.navigation` 里塞自己的 `<a>`，顺序由 `priority` 与注册顺序偶然决定，
   站点无法表达"我要的是：首页 → 关于 → 分类入口 → GitHub"这样一条确定顺序。
2. **导航的范围被内容插件绑架**：`rice.pages` 曾有一个 `navLimit` 设置
   （"导航最多展示多少个页面"）。导航总量本该由"谁拥有导航"决定，
   而不是由某个内容插件的配置决定；两个来源各有一个上限时，用户无法推理最终结果。
3. **展示逻辑与内容领域耦合**：页面插件的责任是"有哪些页面、内容是否合法"，
   而"哪些进导航、第几位、显示什么文案、是否新窗口"属于**站点结构**，
   与内容本身无关，也不该由内容插件的生命周期决定。

## 决策

1. **导航栏归 `rice.navigation` 独占**：只有它注册 `header.navigation`，
   也只有它拥有"导航项"这一实体（表 `rn_nav_items`）。
2. **页面插件不再注册任何插槽**，只保留 `navItems()` 作为"已发布页面清单"的查询入口，
   供导航插件解析引用目标。
3. **导航项是"引用"，不是快照**：`page` / `post` 类型只保存 `ref_id`，
   标题与前台地址在读取时向内容插件解析（`content.pages@1` / `content.posts@1`）。
   内容改名改别名后导航自动跟随；目标被删除或未发布时，**前台跳过该项**
   （绝不输出死链），后台则用 `exists` / `published` 明确提示。
4. **目标解析失败是一等公民**：不建跨插件外键、不冗余保存标题，
   解析失败既不是数据库错误也不是渲染异常，而是"这一项暂时不显示"。
5. **导航项变化必须清空 HTML 缓存**：导航插槽出现在每个页面上，按标签精确失效覆盖不到。
   内容侧变化则先在 `rice.navigation` 内判定"该内容是否被引用"，
   只有被引用时才清缓存（否则每次保存文章都会清全站缓存）。
6. **v1 只做一级导航**（不做下拉二级菜单）。需要层级时，
   下一版通过新增 `parent_id` 迁移 + 主题下拉样式实现，属**加法**变更，不破坏现有数据。

## 明确不做的事

- 不做"页面自动进导航"的隐式行为（哪怕默认关闭的开关也不做：
  开关一旦存在，用户仍然要理解两套模型）；
- 不做可视化拖拽排序（上下移按钮已足够表达顺序，且无第三方依赖）；
- 不允许主题注册导航项：主题是展示层，数据来源必须可审计（后台可见、可编辑）。

## 理由

- **单一所有权**：一个插槽只有一个写入者，"为什么导航顺序是这样"有唯一答案；
- **引用优于快照**：站点结构（导航）与内容（标题、地址）各自演进，
  引用让"改个页面标题"不需要同时改导航，也不会出现"导航里的旧标题"；
- **失败可解释**：删除内容后导航项自动不显示、后台明确提示，
  比"导航里留一个 404 链接"或"数据库报外键错误"都更可运维；
- **能力对等**：第三方插件也能通过同一个 `content.navigation@1` 读取导航，
  不需要知道 `rn_nav_items` 的存在。

## 后果

**正面**

- 导航栏成为可排序、可停用、可跨来源编排的站点结构，与内容插件解耦；
- 内容插件的生命周期不再影响导航的其余部分（禁用 posts 后，页面与自定义链接照常显示）；
- 页面插件卸下了 `navLimit` 与展示逻辑，职责回归"内容"。

**负面 / 约束**

- 用户多了一步：新建页面后需要在「导航栏」里引用它才会出现在导航中
  （这是刻意的：导航是站点结构的显式表达）；
- 后台出现第二个内容相关的入口（「页面」与「导航栏」），需要在文案上引导；
- 导航渲染依赖内容插件的服务可用性，禁用内容插件时引用类导航项会静默不显示
  （后台有提示，前台无占位）。
