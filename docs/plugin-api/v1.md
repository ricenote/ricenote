# RiceNote Plugin API v1

> 稳定契约。本文件与 `packages/plugin-sdk`、`packages/shared` 的导出保持一一对应；
> 变更 SDK 必须同步修订本文并追加 ADR。

## 1. 目录即插件

一个插件就是一个目录，放入 `PLUGINS_DIR`（默认 `plugins/official/`）即被发现：

```
plugins/official/posts/
├── manifest.json        # 必需：插件清单
├── package.json         # 推荐：工作区包，便于独立构建
├── src/                 # 源码
├── dist/                # 构建产物（manifest.entry 指向这里）
└── migrations/          # 可选：SQL 迁移，Core 加锁串行执行
    └── 0001_init.sql
```

## 2. manifest.json 契约

由 `packages/shared/manifests/plugin.schema.json` 校验（Ajv）。

```json
{
  "schemaVersion": 1,
  "id": "rice.posts",
  "name": "文章",
  "version": "1.0.0",
  "apiVersion": "^1.0.0",
  "entry": "./dist/index.js",
  "requires": { "identity.users@1": "^1.0.0" },
  "provides": ["content.posts@1"],
  "capabilities": ["routes:public", "routes:admin", "database:own", "events:publish", "slots:register"],
  "migrations": "./migrations",
  "settings": { "pageSize": 10 }
}
```

| 字段 | 必需 | 说明 |
| --- | --- | --- |
| `schemaVersion` | 是 | 固定 `1` |
| `id` | 是 | 唯一标识，形如 `rice.posts` |
| `name` | 是 | 显示名 |
| `version` | 是 | 语义化版本 |
| `apiVersion` | 是 | 依赖的 Plugin API 区间，如 `^1.0.0` |
| `entry` | 是 | 相对插件目录的入口模块（`./` 开头） |
| `requires` | 否 | 依赖：键为 **capability 契约** 或插件 ID，值为 semver 区间 |
| `provides` | 否 | 对外提供的 capability 契约 |
| `capabilities` | 否 | 请求的内核能力白名单 |
| `migrations` | 否 | 迁移目录 |
| `settings` | 否 | 插件配置**默认值**（扁平「字段名 → 值」）。旧写法，语义自 v1 起未变 |
| `settingsSchema` | 否 | 插件设置的**声明式表单定义**（分组 + 字段），见第 12 节 |
| `permissions` | 否 | 本插件**拥有**的权限点声明（`key` + `label` + `group`），见第 19 节 |

> `settings` 与 `settingsSchema` 可以共存：合并顺序是「`settings` 默认值 → `settingsSchema` 默认值 → 数据库覆盖」，
> 因此声明了 `settingsSchema` 的字段以表单声明为准。新插件建议只用 `settingsSchema`。

### 能力白名单

`routes:public`、`routes:admin`、`database:own`、`events:publish`、`events:subscribe`、
`services:provide`、`services:consume`、`slots:register`、`admin:menu`、`media:store`。

未声明 `database:own` 的插件调用 `ctx.db` 会抛出 `RN_FORBIDDEN`；
未声明 `routes:admin` 的插件调用 `ctx.routes.adminApi()` 同样被拒绝。

## 3. 依赖解析规则

1. `requires` 的键若形如 `content.posts@1`，按 **capability** 解析：找到提供该契约且版本满足区间的插件。
2. 否则按 **插件 ID** 解析（仅在确需特定实现时使用）。
3. 解析后进行**拓扑排序**；出现环或版本冲突时启动失败并明确报错：
   - `RN_DEPENDENCY_MISSING`
   - `RN_DEPENDENCY_VERSION_CONFLICT`
   - `RN_DEPENDENCY_CYCLE`
4. 禁用被依赖插件时返回 `RN_DEPENDENCY_DISABLED` 并列出依赖者。

## 4. 生命周期

```
DISCOVERED → VALIDATED → INSTALLED → ENABLED → STARTED → STOPPED / DISABLED
                                                     ↘ FAILED（独立记录，不阻塞其他插件）
```

| 阶段 | 钩子 | 允许做什么 |
| --- | --- | --- |
| 安装 | `setup(ctx)` | 注册迁移、准备静态资源、读取配置。**不得注册路由** |
| 启用 | `start(ctx)` | 注册路由、订阅事件、注册 Slot、发布服务 |
| 停用 | `stop(ctx)` | **必须**调用全部 `Dispose` / `Unsubscribe` 句柄 |

> 启停为**受控重启**语义（ADR-004）：状态写入 `rn_plugins`，路由变更需重启进程生效。
> 但注册表状态必须在 `stop()` 后完全干净。

## 5. 代码示例

```ts
import { definePlugin } from '@ricenote/plugin-sdk';

export default definePlugin({
  setup(ctx) {
    ctx.logger.info('posts 插件安装完成');
  },

  start(ctx) {
    ctx.services.provide({
      name: 'content.posts@1',
      version: '1.0.0',
      implementation: {
        findPublished: async (limit: number) =>
          ctx.db.query('select id, title, slug from rn_posts where status = ? limit ?', [
            'published',
            limit
          ])
      }
    });

    ctx.routes.page({
      name: 'post.show',
      path: '/post/:slug',
      kind: 'post',
      handler: async (request) => {
        const rows = await ctx.db.query<{ id: number; title: string; content_html: string }>(
          'select id, title, content_html from rn_posts where slug = ? and status = ? limit 1',
          [request.params.slug, 'published']
        );
        const post = rows[0];
        if (!post) {
          return { kind: '404', title: '文章不存在', status: 404, data: {} };
        }
        return {
          kind: 'post',
          title: post.title,
          canonicalUrl: `/post/${request.params.slug}`,
          data: { post: { ...post, url: `/post/${request.params.slug}` } },
          cacheTags: [`post:${post.id}`]
        };
      }
    });

    const off = ctx.events.on('content.post.published.v1', (payload) => {
      ctx.logger.info('收到发布事件', { payload });
    });

    ctx.routes.raw({
      method: 'GET',
      path: '/feed.xml',
      handler: (_req, reply) => reply.header('content-type', 'application/xml').send('<rss/>')
    });

    // 必须保存句柄以便 stop() 注销
    stopHandles.push(off);
  },

  stop(ctx) {
    for (const off of stopHandles) off();
    stopHandles.length = 0;
  }
});

const stopHandles: Array<() => void> = [];
```

## 6. 两条必须遵守的启动期约定

### 6.1 不要在 `start()` 里做"需要其他插件已就绪"的初始化

拓扑排序只保证 **依赖在前**，不保证任意两个无依赖关系的插件之间的先后顺序。
如果 A 插件的初始化需要 B 插件已经完成订阅或已发布服务，请把它挂到 Core 广播的
生命周期事件上：

```ts
ctx.events.on('core.runtime.started.v1', async () => {
  // 此时全部插件都已完成 start()，事件订阅与服务注册均已就位
  await service.ensureBootstrapAdmin(setup.bootstrapAdmin());
});
```

`core.runtime.started.v1` 由 Core 在**所有插件启动完成后**发布，payload 为
`{ started: string[], failed: string[], excluded: string[] }`。
identity 插件正是通过它创建初始管理员，从而确保 authorization 插件能收到
`identity.user.created.v1` 并完成角色分派。

### 6.2 可选依赖必须在请求期惰性解析

```ts
// 反例：start() 里一次性取用，若对方尚未启动（或已被禁用）会静默降级
const taxonomy = ctx.services.tryUse<TaxonomyService>('content.taxonomy@1');

// 正例：把解析器放进运行时容器，用到时再取
const taxonomy = runtime.services.tryUse<TaxonomyService>('content.taxonomy@1');
```

`tryUse` 不会因缺失而报错，但**解析时机**决定了正确性：
在 `start()` 中解析可能因为对方还没启动而得到 `undefined`（假阴性），
导致插件看似可用却功能缺失。posts 插件对 taxonomy / media / identity.users
三个可选依赖全部采用请求期解析。

### 6.3 停用后的"零残留"是硬性承诺

`ctx.routes.*`、`ctx.services.provide`、`ctx.events.on`、`ctx.slots.register`、
`ctx.adminMenu.add` 返回的句柄都会被 Core 记录：

- `stop()` 中应主动调用全部句柄（推荐做法，语义清晰）；
- 若忘记调用，Core 会在 `stop()` 之后**兜底释放**，保证注册表干净；
- `PluginManager.assertNoLeaks()` 会断言已停用插件在
  路由 / 服务 / Slot / 后台菜单 / 事件订阅中**零残留**，集成测试依赖此断言。

## 7. PluginContext 参考

| 成员 | 说明 |
| --- | --- |
| `manifest` | 只读的规范化 Manifest |
| `logger` | 结构化日志，自动附加插件 ID 与请求 ID |
| `config` | `get(key, fallback)` / `all()`，值为 Manifest 默认值与站点覆盖合并结果。**启动期快照**：修改后需重启才生效 |
| `db` | `query` / `execute` / `transaction` / `table(name)` / `orm`（Drizzle 句柄） |
| `services` | `provide` / `use` / `tryUse` / `has` / `list` |
| `events` | `on(name, handler, { priority })` → `Unsubscribe`；`emit(name, payload)` |
| `routes` | `page` / `raw` / `adminApi`，均返回 `Dispose` |
| `slots` | `register(slotName, component, { priority })` → `Dispose` |
| `adminMenu` | `add({ id, label, path, icon?, order?, permission? })` → `Dispose` |
| `site` | 站点信息 `{ id, title, description, url, language, logoUrl?, faviconUrl?, icpText?, icpUrl? }`。**动态取值**：每次访问都读当前生效值，后台改了站点信息无需重启即可看到 |

> `config` 与 `site` 的时效性差异是刻意的：
> 插件配置可能决定路由/服务如何注册（启动期装配），因此保持快照语义（ADR-004）；
> 站点信息只影响展示，因此实时读取（ADR-011）。

### 数据库约束

- 表名必须由 `ctx.db.table('posts')` 生成（结果形如 `rn_posts`），禁止硬编码他人表名；
- **禁止跨插件联表**：需要他人数据时调用其服务（`ctx.services.use('identity.users@1')`）；
- 迁移只能通过 `manifest.migrations` 声明 SQL 文件，由 Core 加锁串行执行；
- 插件停用**不会**自动 drop 表。

### 事件命名与一致性

- 业务事件统一格式：`<域>.<实体>.<动作>.v<主版本>`，例如 `content.post.published.v1`；
- 事件总线**不保证持久性**，不得用于强一致场景；
- 需要"立即知道"的场景请使用**同步服务调用**；
- 需要不丢事件时使用 MySQL Outbox（接口已预留，`packages/core/src/events/outbox.ts`）。

## 8. 错误码

插件应抛出 `RiceNoteError`（来自 `@ricenote/shared`）并携带稳定错误码，
HTTP 层会据此生成响应。常用错误码见 `packages/shared/src/errors.ts`。

## 9. 版本兼容策略

- `apiVersion` 使用 semver 区间；Core 在启动时校验并拒绝不满足的插件。
- v1 承诺：新增能力以**可选字段**引入；不改变既有方法签名。
- 破坏性变更需提升 Plugin API 主版本，并保留旧版本适配层至少一个大版本。

## 10. 跨插件服务契约

由官方插件提供的契约（Core 自身提供的契约见第 15 节）：

| 契约 | 提供者 | 典型消费方 | 用途 |
| --- | --- | --- | --- |
| `identity.auth@1` | `rice.identity` | Core（会话解析） | 登录、会话、改密、重置密码、资料 |
| `identity.users@1` | `rice.identity` | `rice.posts`（硬依赖）、`rice.comments`、`rice.authorization` | 用户公开信息与显示名 |
| `identity.authorization@1` | `rice.authorization` | `rice.identity`、`rice.posts` | 角色与权限查询 |
| `content.posts@1` | `rice.posts` | `rice.comments`、`rice.seo`、`rice.navigation` | 文章读取与后台管理 |
| `content.pages@1` | `rice.pages` | `rice.navigation`、第三方插件 | 自定义页面读取与后台管理 |
| `content.navigation@1` | `rice.navigation` | 主题（经插槽）与第三方插件 | 导航项读取、增删改与排序 |
| `content.taxonomy@1` | `rice.taxonomy` | 第三方插件 | 分类与标签 |
| `taxonomy.internal@1` | `rice.taxonomy` | `rice.posts` | 文章↔词条关联维护（官方插件间约定） |
| `media.library@1` | `rice.media` | `rice.posts`、后台站点设置 | 上传、元数据与访问地址 |
| `content.search@1` | `rice.search` | `rice.posts` 等数据源拥有者 | 可搜索数据源注册表 |
| `content.comments@1` | `rice.comments` | 后台仪表盘、第三方插件 | 评论读取、提交与审核 |

**依赖方向提醒**：只有在"没有它就无法工作"时才写进 `requires`。
像 `content.search@1` 这种"对方被动接收注册"的契约绝不能写进 `requires`，
否则 search 被禁用时你的插件会直接启动失败。

```ts
// 数据源拥有者向 search 注册（posts 的实际做法）
const search = ctx.services.tryUse<ContentSearchService>('content.search@1');
if (search) search.registerSource(createPostsSearchSource(runtime));

// 停止时必须注销：注册表在 search 插件自己的进程内存中
ctx.services.tryUse<ContentSearchService>('content.search@1')?.unregisterSource('posts');
```

约定与注意事项：

- **注册方向是"数据源拥有者主动注册"**，因此 `search` 与数据源之间**没有硬依赖**：
  不要把 `content.search@1` 写进 `requires`（那会变成硬依赖，search 被禁用时你的插件无法启动）。
- 注册时机应在 **`core.runtime.started.v1`**：拓扑排序不保证无依赖插件之间的先后顺序，
  在 `start()` 里直接取服务会出现"对方还没启动"的假阴性。
- 检索实现（含索引维护）归数据源所有：`rice.search` **不越权查询 `rn_posts`**。
- 单个数据源抛错被隔离，只影响它自己的结果。

`content.comments@1` 的关键方法：`submit()`（前台提交，返回 `{ id, status }`）、
`listApprovedThreaded()`（前台线程化读取）、`listForAdmin()` / `moderate()` / `countByStatus()`（后台审核）。

## 11. 安装、升级与分发

### 目录即插件（开发期）

把插件目录放到 `config.paths.pluginsDir`（默认 `plugins/official`）、
`config.paths.pluginsInstallDir`（默认 `plugins/third-party`），
或用 `RICENOTE_LOCAL_PLUGINS`（逗号分隔）登记任意本地根目录，都会被自动发现。
ID 去重跨根目录生效。

> **本地开发目录不需要"安装"**：登记后开发环境会监视其变化并**自动重启内核**
> （900ms 抖动合并），实现"改动即生效"。注意这是重启而非模块级 HMR ——
> Node 的 ESM 模块缓存按 URL 生效，进程内重启不会重载代码（ADR-012）。

### 三种安装来源（v0.4.0，ADR-015）

| 来源 | 形态 | 依赖与构建 |
| --- | --- | --- |
| `registry` | npm 包名（可带版本区间，如 `ricenote-nav@^1.2.0`） | 自动装依赖（`--prod`，需构建时装 devDependencies），按需执行 `scripts.build` |
| `git` | `repo + ref`（tag / 提交 / 分支） | 取源码后按 `scripts.build` 构建 |
| `local` | 目录路径，或压缩包（`via: 'zip'`） | 目录按 `package.json` 处理；压缩包不参与版本管理 |

后台：`POST /api/admin/plugins/install/source`（JSON 来源）、
`POST /api/admin/plugins/install`（multipart 压缩包）、`POST /api/admin/plugins/:id/update`、
`POST /api/admin/plugins/:id/remove`、`GET /api/admin/plugins/updates`、
`GET /api/admin/plugins/jobs[/:jobId]`。
CLI：`ricenote plugin install|update|remove|jobs|updates`（与后台共用同一编排与任务队列）。

**权限**：写操作需要 `plugin.install`（默认仅 `administrator`）；读列表/任务需要 `plugin.view`。

**编排三段式**（不可逆动作压到最后一刻，失败必回滚）：

1. `resolve`：把来源变成工作区里一个含 `manifest.json` 的目录（网络/磁盘错误都在这里）；
2. `prepare`：校验清单与入口 → 装依赖 → 执行构建（构建后**重新校验**入口，因为入口可能是构建产物）；
3. `commit`：复制到 `<target>.incoming-*` → 旧目录改名为 `<target>.backup-*` →
   incoming 转正 → 删除备份。任一步失败即还原备份。

其他约定：

- 依赖装在**插件目录内**（`<pluginDir>/node_modules`），落盘后 Node 从模块位置向上查找即命中；
- 复制时排除 `node_modules`；发现机制跳过 `.incoming-*` / `.backup-*` / 点开头目录；
- 依赖里含 `workspace:` 协议（单调仓库内的插件）会**跳过依赖安装**并使用其构建产物
  —— 这类插件请用本地开发目录登记，而不是"安装一份拷贝"；
- 安全限额：32MB 压缩包 / 2000 条目 / 单文件 16MB / 解压总计 96MB；
  扩展名白名单 `.js .mjs .cjs .json .sql .md .txt .map .css .html .wasm` 与字体图片，
  **仍禁止 `.node`**；解包统一走 zip-guard 两阶段校验；
- npm 包做 **sha512 完整性校验**；Git 地址走白名单（拒绝 `ext::` / `file://` / 本地路径）；
- 私有源 `RICENOTE_NPM_REGISTRY` / `RICENOTE_NPM_TOKEN` 只从环境变量读取，不落库、不进日志；
- **安装第三方插件等同授予其服务器代码执行权限**（可执行依赖安装与构建脚本）：
  后台以高风险确认框明示并写入审计；`RICENOTE_ALLOW_INSTALL_SCRIPTS=false` 可全局禁用脚本执行；
- 同 ID 覆盖安装即升级；目标目录被**其他 ID** 占用时拒绝（409）；
- 安装后按 ADR-004 受控重启生效（任务完成后扩展中心与顶栏都会提示）。

### SDK 由宿主提供（重要）

插件**不需要**自带 `node_modules`：`@ricenote/plugin-sdk`、`@ricenote/shared`、`@ricenote/theme-sdk`
由宿主进程提供，因此插件包里写 `import { definePlugin } from '@ricenote/plugin-sdk'`
在运行时可以被解析。

实现方式：这三个包同时是**仓库根目录的依赖**。Node 解析裸模块说明符时会从
`plugins/third-party/<id>/dist/index.js` 逐级向上查找，最终在 `<项目根>/node_modules` 命中，
因此 ZIP 安装（无 `node_modules`）的插件也能正常加载。

由此产生两条打包要求：

1. 插件包内**不要**打包自己的 `node_modules`（会被类型白名单拒绝，属非必要文件）；
2. 除上述宿主提供的包之外，其他第三方依赖必须**打包进产物**（插件没有包管理器）。

> 这也是"v1 插件无真实沙箱"的另一面：宿主与插件共享同一个进程与模块图，
> 因此只允许安装受信任插件。

### 升级与迁移

- 迁移文件名即记录名（如 `0002_add_note.sql`），按文件名升序执行；
- **已应用的迁移按内容校验（SHA-256）**：历史文件被改写会拒绝启动，而不是静默重跑；
- 插件目录回退到旧版本不会重复执行已应用的迁移；
- 已应用迁移的内容不可改，只能新增迁移文件。

### 第三方示例

`plugins/third-party/reading-time/` 是最小第三方插件：只声明 `slots:register` 一个能力，
不依赖任何其他插件、不持有数据表、不注册路由，仅通过标准 Slot `post.beforeContent`
注入一行阅读时长。它可作为第三方插件的起手模板。

它同样声明了 `settingsSchema`（「展示」分组），用来证明**声明式设置对第三方与官方插件完全等价**：
不需要额外能力、不需要写后台界面代码，后台就会自动生成表单与校验。

## 12. 插件设置（1.1.0 新增）

### 12.1 两种写法

**旧写法**（`settings`，继续支持）：

```json
"settings": { "pageSize": 10, "excerptLength": 160 }
```

插件内 `ctx.config.get('pageSize', 10)`；后台设置面板退化为键值编辑，
且**只允许写入已声明的键**（防止借该接口往任意配置塞东西）。

**新写法**（`settingsSchema`，推荐）：

```json
"settingsSchema": {
  "general": {
    "label": { "zh-CN": "通用", "en": "General" },
    "description": { "zh-CN": "影响前台展示", "en": "Affects the public site" },
    "fields": {
      "listPageSize": {
        "type": "number",
        "label": { "zh-CN": "列表每页条数", "en": "Items per page" },
        "default": 20,
        "min": 1,
        "max": 100
      },
      "blockedKeywords": {
        "type": "stringList",
        "label": { "zh-CN": "屏蔽关键词", "en": "Blocked keywords" },
        "description": { "zh-CN": "每行一项", "en": "One per line" },
        "default": [],
        "maxItems": 200,
        "maxLength": 60
      }
    }
  }
}
```

- 结构与**主题设置完全一致**（同一份 JSON Schema 定义 `packages/shared/manifests/settings.schema.json`）；
- 字段类型白名单：`text` / `textarea` / `color` / `boolean` / `number` / `select` / `image` / `url` / `stringList`；
- `label` / `description` / `placeholder` / `options[].label` 支持多语言对象，运行时按站点语言解析；
- 后台据此**自动生成表单**，并做服务端二次校验（类型、`min`/`max`、`maxLength`、`maxItems`、枚举、URL 格式）。

**默认值只写一处**：新写法把默认值放在 `settingsSchema` 各字段的 `default`，
不要再同时保留旧写法 `settings`（两处都写必然漂移：后台显示一个值、插件按另一个值运行）。
旧写法仅为既有插件保留。

字段类型与后台控件、存储值类型的对应关系：

| 类型 | 后台控件 | 存储值 | 附加约束 |
| --- | --- | --- | --- |
| `text` / `textarea` | 输入框 / 多行输入 | `string` | `maxLength` |
| `url` | 输入框（type=url） | `string` | 必须 `http(s)://` 开头 |
| `color` | 取色器 + 输入框 | `string` | CSS 颜色白名单 |
| `boolean` | 开关 | `boolean` | `default` 必须为布尔 |
| `number` | 数字输入 | `number` | `min` / `max` |
| `select` | 下拉 | `string` | 必须提供 `options` |
| `image` | 输入框 | `number`(媒体 ID) 或受管相对路径 | 不允任意服务器路径 |
| `stringList` | 多行输入（每行一项） | **`string[]`** | `maxItems`（默认 200）、`maxLength`（单项长度） |

`stringList` 的值在存储、DTO 与插件侧**都是数组**，因此插件可以直接：

```ts
const blocked = ctx.config.get<string[]>('blockedKeywords', []);
```

提交时也接受"按行分隔的字符串"（服务端会拆分成数组），这样自建表单或直接调 API
的调用方不必自己处理拆分；空行与首尾空白一律丢弃。官方用例见
`plugins/official/comments`（`blockedKeywords`）与 `plugins/official/seo`（`robotsDisallow`）。

### 12.2 读取配置

`ctx.config.get(key, fallback)` 与 `ctx.config.all()` 读取的是
「`settings` 默认值 → `settingsSchema` 默认值 → 数据库覆盖」的合并结果。

> 后台设置表单用的是**同一个合并函数**（`resolvePluginSettings`），
> 所以"表单里显示的值"与"插件实际读到的值"必然一致——不存在两套默认值。

合并发生在**插件启动时**，因此：

> 修改插件设置后必须**重启服务**才生效。后台保存后会标记"待重启"，
> 顶栏出现「重启」按钮，点击即可完成进程内软重启（ADR-012）。

要注意两类"重启"的区别（详见 ADR-012 的约束）：

| 变更 | 生效方式 |
| --- | --- |
| 插件设置、插件启停、主题设置、站点信息、数据库内容 | 后台「重启」按钮（进程内软重启）即可 |
| **插件/内核/主题模板的代码或文件**（改了 `src/`、`theme.json`、`*.njk` 后 `pnpm build`） | **必须重启进程**：Node 的 ESM 模块缓存按 URL 生效，进程内重启不会加载新的 `dist` 产物 |

### 12.3 后台接口

| 方法 | 路径 | 权限点 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/admin/plugins/:pluginId/settings` | `plugin.view` | 返回 `{ groups, values, revision, declarative }` |
| PUT | `/api/admin/plugins/:pluginId/settings` | `plugin.manage` | 保存（**合并式**：只覆盖提交的字段），并标记待重启 |

保存是合并而不是整体替换，因此局部提交不会清空其他字段；
未声明的键返回 `RN_PLUGIN_SETTING_INVALID`，`details.issues` 给出字段级问题。

### 12.4 自定义设置页（兜底方案）

需要复杂交互（测试连接、列表编辑等）的插件可以不声明 `settingsSchema`，
改为注册自己的后台页面 —— 即第 16 节的「插件自带后台界面」：

```json
"admin": {
  "pages": [
    { "id": "my.settings", "label": "我的插件设置", "path": "/my-settings",
      "icon": "Settings", "order": 60, "permission": "plugin.manage",
      "entry": "./admin/settings.js" }
  ]
}
```

```ts
// 设置读写仍走自己的管理 API（Core 统一套用认证/CSRF/权限/审计）
ctx.routes.adminApi({ method: 'GET', path: '/my/options', permission: 'plugin.manage', handler: ... });
```

界面完全由插件实现，并自动获得加载态、错误边界、未启用提示与设计令牌；
详见第 16 节。

## 13. 全部扩展点（Hook）清单

RiceNote **没有** `ctx.hooks` 之类的通用钩子 API；插件与站点交互的全部通道就是
`PluginContext` 暴露的下列 5 类注册面。跨插件的完整实测清单（含每个官方插件用到哪些）
见 `docs/architecture/hooks-inventory.md`。

| 类别 | API | 说明 |
| --- | --- | --- |
| 公开页面路由 | `ctx.routes.page({ name, path, kind, template?, cacheable?, handler })` | 产出 ViewModel，由主题渲染；`name` 供 `url()` 生成链接 |
| 原始 HTTP 路由 | `ctx.routes.raw({ method, path, capability?, handler })` | RSS / sitemap / 表单提交 / 数据读取等非页面路由 |
| 管理 API | `ctx.routes.adminApi({ method, path, permission?, handler })` | 自动套用认证 → CSRF → 权限 → 审计 |
| 插槽 | `ctx.slots.register(slotName, { name, render }, { priority? })` | 向主题固定挂载点注入 HTML 片段 |
| 服务契约 | `ctx.services.provide(...)` / `use` / `tryUse` | 插件间协作的唯一通道 |
| 事件 | `ctx.events.on(name, handler, { priority? })` / `emit(name, payload)` | 松耦合广播（不保证持久性） |
| 后台菜单 | `ctx.adminMenu.add({ id, label, path, icon?, order?, permission? })` | 向后台上方导航贡献入口 |
| 生命周期 | `definePlugin({ setup?, start, stop })` | 安装 / 启用 / 停用三个时机的唯一入口 |

### 13.1 标准插槽（说明书 7.7）

`head.end`、`body.start`、`body.end`、`header.navigation`、`sidebar.widgets`、
`post.beforeContent`、`post.afterContent`、`post.comments`、`footer.widgets`。

顺序：按 `priority` 降序，同优先级按注册顺序；**单组件异常被隔离**（降级为空片段并记日志），
不会让整页渲染失败。

实现示例（`plugins/official/navigation/src/slot.ts`）：

```ts
ctx.slots.register(
  'header.navigation',
  {
    name: 'navigation.header',
    render: async (context) => {
      const items = await service.listRenderable();
      if (items.length === 0) return '';
      // 当前项由插槽负责判定：主题按 aria-current 高亮，不自算
      return items
        .map((item) => {
          const active = isActiveNavHref(item.href, currentPathOf(context.request?.url));
          return `<a href="${escape(item.href)}" class="rn-nav-link${
            active ? ' rn-nav-link--active' : ''
          }"${active ? ' aria-current="page"' : ''}>${escape(item.label)}</a>`;
        })
        .join('');
    }
  },
  { priority: 20 }
);
```

> 插槽输出会被原样插入页面，因此**必须自行转义**：用 `core.html@1` 的 `escape()`，
> 或对富文本先 `sanitize()` 再 `markTrusted()`。
>
> 同一个插槽被多个插件抢占会让主题拿到重复内容，因此"谁拥有全局展示"要在设计上明确：
> 例如顶部导航栏由 `rice.navigation` 独占，页面插件只提供"有哪些页面"（`content.pages@1`）。

### 13.2 事件命名

`<域>.<实体>.<动作>.v<主版本>`，例如 `content.post.published.v1`。
现有事件全表见 `docs/architecture/hooks-inventory.md`。

## 14. 页面类型、模板与内容约定

### 14.1 `kind` 与模板回退链

插件在 `ctx.routes.page` 中声明的 `kind` 是**主题与插件之间的契约**：
主题用 `theme.json` 的 `templates[kind]` 指定模板文件。

渲染器选择模板的顺序：

```
显式模板（PageViewModel.template / PageRouteSpec.template）
  → theme.manifest.templates[kind]
    → 主题 fallback.njk
      → Core 内置 fallback.njk
```

`template` 支持两种写法：**主题声明的模板键**（推荐，内容存的就是它）或直接的 `.njk` 文件名。
两者都必须落在主题模板目录内，不存在目录穿越可能。

### 14.2 让内容可选主题模板（1.1.0 新增）

```ts
// 页面/文章保存时校验，运行时读取
const theme = ctx.services.use<CoreThemeService>('core.theme@1');
const available = await theme.pageTemplates();   // 当前主题声明的模板清单
```

- 主题用 `pageTemplates` 声明可选项（键 → 模板文件 + 多语言 label）；
- 内容只存**键**，因此主题更换模板文件名不会让旧数据失效；
- 保存时用 `resolveContentTemplateKey(raw, available)`（`@ricenote/shared` 导出）
  校验并归一化；键失效时渲染器回退到 kind 模板而**不报错**。

现有 kind 约定：`home`（首页）、`post`（文章详情）、`page`（自定义页面）、
`archive`（分类/标签归档）、`search`（搜索结果）、`404`（未找到）。

## 15. Core 提供给插件的服务契约（1.1.0 新增两个）

| 契约 | 说明 |
| --- | --- |
| `core.security@1` | 注册会话解析器与权限解析器（依赖倒置，Core 不 import 插件） |
| `core.theme@1` | `activeThemeId()`、`settings()`（当前主题设置）、**`pageTemplates()`**（可选模板清单）、`invalidate(tags)`（按标签失效 HTML 缓存）、**`clearCache()`**（清空全部缓存，用于内容出现在全局插槽时） |
| `core.html@1` | `sanitize()` / `markTrusted()` / `escape()`：全站统一的富文本安全化 |
| `core.setup@1` | `siteId()`、`bootstrapAdmin()`、`paths()`（受管目录） |
| **`core.site@1`** | `info()`：当前生效的站点信息（env 默认值 + 后台覆盖），同步返回，可在渲染热路径调用 |
| **`core.runtime@1`** | 待生效状态与重启：`markRestartRequired()`、`requestRestart()`、`state()`、`clearRestartRequired()`、`registerRestartHandler()` |

### 15.1 申请重启（插件也能用）

如果某个变更必须重启才能生效（例如你自己实现了类似的"装配期配置"），可以：

```ts
const runtime = ctx.services.use<CoreRuntimeService>('core.runtime@1');
await runtime.markRestartRequired({ reason: '插件配置已保存，重启后生效' });
// 或：请求立即重启（仅当进程入口注册了执行器时才可用）
await runtime.requestRestart({ reason: '插件请求重启' });
```

后台顶栏的「重启」按钮就是基于 `GET /api/admin/system/state` 的这个状态显示的。

## 16. 插件自带后台界面（v0.4.0）

插件不再需要 Core 为它写页面：界面代码放在插件目录的 `admin/` 下，
由 Core 托管、由后台动态加载。**零构建**：写一个 `.js` 文件即可，不装依赖、不跑打包。

### 16.1 目录约定

```
plugins/official/navigation/
├── admin/
│   ├── main.js         必需：界面入口（纯 ESM，默认导出一个页面组件）
│   └── style.css       可选：插件自有样式（存在时由宿主动态注入）
├── dist/               服务端代码产物（tsc）
└── manifest.json
```

### 16.2 声明（`manifest.json`）

```json
"admin": {
  "pages": [
    {
      "id": "navigation.items",
      "label": "导航栏",
      "path": "/navigation",
      "icon": "Navigation",
      "order": 18,
      "permission": "nav.view",
      "entry": "./admin/main.js"
    }
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 菜单项 ID，全局唯一（`^[a-z][a-z0-9._-]{1,80}$`） |
| `label` | 是 | 菜单显示名 |
| `path` | 是 | 后台路由路径，`/` 开头且全局唯一（保持既有书签可用） |
| `icon` | 否 | 图标名（见 16.4 的受控图标集） |
| `order` | 否 | 排序权重，数值越大越靠前 |
| `permission` | 否 | 访问所需权限点；为空表示仅需登录 |
| `entry` | 是 | 相对插件目录的入口模块，形如 `./admin/main.js` |
| `style` | 否 | 可选：相对插件目录的样式文件，形如 `./admin/style.css`；声明后由宿主注入（**不声明就不加载**，避免探测文件产生 404 噪声） |

Core 会：注册菜单（随插件启停一起生效与回收）、把 `entry` 换算成前端可直接
`import()` 的 URL（`/plugin-admin/<pluginId>/main.js`）、在启动与 `pnpm validate`
时校验入口文件存在、页面路径与 ID 不冲突。

> 声明式菜单**不需要** `admin:menu` 能力；`ctx.adminMenu.add` 仍可用（兼容路径），
> 但两者混用时注意 ID 与路径不能重复。

### 16.3 模块契约

```js
import { defineAdminPage, ref, computed, api, useToast, useSession } from '/admin-sdk/v1/ricenote-admin.js';

export default defineAdminPage({
  title: '导航栏',
  setup() {
    const session = useSession();
    const toast = useToast();
    const items = ref([]);
    const canManage = computed(() => session.can('nav.view'));

    async function load() {
      items.value = await api.get('/navigation/items');
    }

    return { items, load, canManage, toast };
  },
  template: `
    <AdminPage title="导航栏" description="...">
      <template #actions>
        <Button v-if="canManage" @click="load">刷新</Button>
      </template>
      <DataTable :columns="[{ key: 'label', label: '文案' }]" :rows="items" />
    </AdminPage>
  `
});
```

要点：

1. **只从 `/admin-sdk/v1/ricenote-admin.js` 导入**（浏览器无法解析裸模块名如 `vue`，也不要 import 任何 npm 包）。
2. **组件已全局注册**：模板里直接写 `<AdminPage>`、`<Card>`、`<Button>`、`<DataTable>`、
   `<Dialog>`、`<Select>`、`<Switch>`、`<Badge>`、`<Input>`、`<Textarea>`、`<Label>`、
   `<Field>`、`<Pagination>`、`<Tabs>`、`<EmptyState>`、`<LoadingState>`、`<ConfirmDialog>`、
   `<Icon>`、`<Toaster>`、`<ContentFields>`，不需要在 JS 里注册。
3. `template` 用运行时编译器（依赖当前无 CSP 的环境，见 ADR-014）；也可以改用 `render()`。
4. 宿主负责外壳（侧栏/顶栏）与页面容器，插件只描述"页面内容是什么"。

### 16.4 SDK 能力清单

| 能力 | 说明 |
| --- | --- |
| `api` / `ApiError` / `saveBlob` | 管理接口客户端（自动带会话 Cookie 与 CSRF，路径为 `/api/admin` 之后） |
| `useSession()` | 当前登录者与权限：`user` / `can(permission)` / `isAuthenticated` |
| `useToast()` | 提示条（渲染在宿主最外层，不会被插件容器裁剪） |
| `useSystemState()` | 运行状态：`restartRequired` / `markPending(reason)` / `restart()` |
| `useAsyncData(loader)` | 统一"加载/错误/重试"状态机 |
| `navigate(path)` | 后台内跳转（由宿主注入路由） |
| `formatDateTime` / `formatDate` / `formatBytes` / `formatDuration` / `cn` | 通用工具 |
| `<Icon name="pencil" />` | 受控图标集（见 `packages/admin-sdk/src/icons.ts`） |
| SDK 版本 | `SDK_VERSION`；`sdkInstanceCount()` 可断言"只有一份实例" |

### 16.5 样式可用范围（重要）

后台的 Tailwind 是**构建期静态扫描**，插件界面（尤其是运行时安装的第三方插件）
不在扫描范围内，因此样式来源有三层：

1. **SDK 组件**（推荐）：外观由组件提供，插件只写结构；
2. **受控工具类白名单**：`apps/admin/tailwind.config.js` 的 `safelist` 收录了布局、
   间距、排版、语义色等安全子集，可直接使用；
3. **插件自带 `admin/style.css`**：由宿主动态注入，适合少量特殊样式。

硬性约束（与 Core 页面一致）：**禁止阴影与毛玻璃**，层级只用 1px 边框与背景色差表达，
主色为柠檬浅黄且黄底上禁用白字。

### 16.6 加载、错误与停用时的行为

后台用通用宿主 `PluginHostView` 加载插件界面，四种状态：

| 状态 | 触发 | 表现 |
| --- | --- | --- |
| 加载中 | 正在 `import()` | 细环指示器 + 页面名 |
| 就绪 | 模块导出默认组件 | 正常渲染 |
| 加载失败 | 模块 404 / 无默认导出 / 抛错 | "插件界面加载失败" + 原因 + 重试 |
| 未启用 | 插件停用或启动失败 | "由插件提供、当前未启用" + 去扩展中心 |

插件组件运行期抛错由宿主的错误边界兜住，**只降级当前页面**并重试，不影响后台其他部分。

### 16.7 安全提示

插件界面脚本在后台**同源上下文**执行，等价于以当前登录用户身份调用任意
`/api/admin/*` —— 这与"插件服务端代码在进程内运行、没有真实沙箱"是同一事实。
**它不是安全沙箱**：只安装可信来源的插件，扩展中心也保留高风险提示。

### 16.8 调试

- 界面资源可单独打开：`GET /plugin-admin/<pluginId>/main.js`（需登录）；
- 浏览器控制台里 `import('/admin-sdk/v1/ricenote-admin.js').then(m => m.sdkInstanceCount())`
  应为 `1`（出现 `2` 说明加载了两份 SDK，通常意味着 base 前缀或缓存配置被改动）；
- 改了 SDK 组件需 `pnpm --filter @ricenote/admin-sdk build`；改了插件界面只需刷新
  （资源为 `no-cache`）。**进程内重启不会重载界面代码**（ADR-012）。

### 16.9 内容字段控件 `ContentFields`（本轮新增）

后台渲染**当前主题声明**的内容自定义字段（声明由宿主 `GET /api/admin/content-fields` 下发，
组件内部已缓存、取数失败降级为空），文章与页面编辑页共用这一个组件，因此"字段长什么样、怎么回填"只有一份实现：

- **契约**：`props { fields?: ContentFieldDto[]; modelValue: Record<string, unknown>; disabled?: boolean }` +
  `emits ['update:modelValue']`。用 `v-model` 绑定内容插件的 `fields` 对象即可（形状与保存载荷一致）；
  `fields` 是**可选覆盖**、一般不用传（缺省用组件自取的主题声明）。
- **声明为空时组件不渲染任何东西**，宿主据此整块隐藏字段区，不必自己判断有无字段；
- 它**不做客户端合法性校验**（只把 `min` / `max` / `maxLength` 等约束透传给控件），
  服务端 `assertContentFieldValues` 才是唯一裁判 —— 前端再判一遍只会与服务端漂移。

详见 `packages/admin-sdk/src/content/ContentFields.vue`；主题侧如何声明见 `docs/theme-api/v1.md` §14。

## 17. 官方插件目录与版本管理（v0.5.0）

官方插件（身份、权限、文章、页面、导航栏、分类标签、媒体、评论、搜索、SEO、订阅、友情链接、编辑增强）
以**独立 npm 包**（`@ricenote/plugin-*`）分发，仓库内仍以 workspace 方式开发。
"装哪些、装哪个版本"由一份随主程序发布的**推荐清单**统一决定。

### 17.1 推荐清单是唯一事实来源

`@ricenote/shared` 内置 `manifests/plugin-catalog.json`（含 Schema，`getPluginCatalog()` 读取并校验）：

```json
{
  "schemaVersion": 1,
  "appVersion": "0.6.0",
  "plugins": [
    {
      "id": "rice.identity",
      "npm": "@ricenote/plugin-identity",
      "version": "1.4.0",
      "category": "required",
      "label": "身份与认证",
      "description": "…",
      "capabilities": ["database:own", "..."],
      "requires": [],
      "repository": "https://github.com/ricenote/plugin-identity",
      "license": "MIT"
    }
  ]
}
```

| 字段 | 用途 |
| --- | --- |
| `category` | `required` 在安装向导中**不可取消**；`recommended` 默认勾选；`optional` 默认不勾；`example` 示例 |
| `version` | **推荐版本**：随主程序测试通过的组合。与 registry 的"最新版本"是两件事，后台的"可更新"以推荐版本为基线 |
| `requires` | 依赖的**其他插件 ID**（不是 capability）：用于勾选联动与安装顺序 |
| `capabilities` | 与 `manifest.capabilities` 保持一致（`pnpm validate` 会核对） |

`required` 只有 `rice.identity` 与 `rice.authorization`，理由是**代码事实**：
缺前者没有 `/api/admin/session`（进不去后台），缺后者安全网关的鉴权全部拒绝。
`ricenote setup --plugins=posts` 也会把这两项强制并入。

### 17.2 安装与更新

```bash
pnpm run setup                             # 向导：自动建库 + 勾选安装（推荐）
pnpm plugin install @ricenote/plugin-posts # 按包名安装（默认取最新）
pnpm plugin updates                        # 检查可用更新
pnpm plugin update rice.posts              # 按已记录来源更新
pnpm plugin remove rice.posts              # 卸载（随仓库分发的那份不可卸载）
```

后台「扩展中心 → 官方插件目录」提供同等能力（沿用安装任务面板：步骤条 + 实时日志）。
**`builtin` 与 `official` 是两个概念**：随仓库分发的插件（`plugins/official`）不可卸载；
从 npm 安装的官方插件同样显示"官方"徽章，但可更新、可卸载。

### 17.3 声明式清单（重建环境可复现）

`.env` 中的 `RICENOTE_PLUGINS`（`包名@区间` 逗号分隔）由向导写出：

```bash

```

启动期**只核对不安装**：声明了但没装、已装版本不满足区间、或声明了未经目录收录的包，
都会在日志里给出可执行命令。`pnpm run setup -- --from-manifest` 按它补齐缺件。

### 17.4 打包契约（插件作者必须遵守）

1. `@ricenote/plugin-sdk` 与 `@ricenote/shared` **只写 `peerDependencies`**，
   并加 `peerDependenciesMeta.<name>.optional = true`：

   ```json
   {
     "peerDependencies": { "@ricenote/plugin-sdk": "^0.6.0", "@ricenote/shared": "^0.6.0" },
     "peerDependenciesMeta": {
       "@ricenote/plugin-sdk": { "optional": true },
       "@ricenote/shared": { "optional": true }
     }
     }
     ```

     > **注意区间语义**：`^0.5.0` 等价于 `>=0.5.0 <0.6.0`，因此**宿主升到 `0.6.0` 时这两个区间必须一起提升**
     > （当前值即 `^0.6.0`），否则插件的 peer 声明会与实际宿主不兼容 —— 宿主是 `0.x` 阶段，
     > 次版本号一涨就跨出了区间。这两行的值跟着根 `package.json` 的版本走
     > （`scripts/split-plugin-repos.mjs` 就是用 `^${appVersion}` 生成的）。
     >
     > 反过来，**`0.6.0 → 0.6.1` 这类补丁升级不需要动区间**：`^0.6.0` 含 `>=0.6.0 <0.7.0`，`0.6.1` 本来就在里面。

   这两个包由**宿主**从项目根 `node_modules` 提供。写成普通 `dependencies` 会在插件目录内
   装出第二份实例（ADR-014 记录过"两份 Vue → 页面空白且控制台干净"同类事故），
   安装编排会直接拒绝这种包；`pnpm validate` 与发布脚本也会拦。

2. `files` 必须含 `dist` 与 `manifest.json`（前者是入口，后者是安装器识别插件的依据）；
   官方插件还统一带 `admin`、`migrations`、`README.md`。
3. `manifest.version` 与 `package.json.version` 必须一致（`pnpm validate` 校验）。
4. 声明了 `scripts.build` 的插件，若同时**不含 `src/` 与 `tsconfig.json`**，
   安装器会视为"只含产物"并跳过依赖安装与构建 —— 从 npm 装的官方插件正是这种形态
   （源码在独立仓库里）。

### 17.5 发布（维护者）

```bash
node scripts/release-plugins.mjs --dry-run          # 先校验并打印将发布的包
NPM_CONFIG_USERCONFIG=/path/to/.npmrc node scripts/release-plugins.mjs
```

脚本按依赖顺序（`shared` → 各 SDK → 插件）逐包 `pnpm publish --access public`，
**发布前**校验版本三处一致、包名与目录一致、`private` 已移除、
`files` 完整、宿主包未写成普通依赖、`dist` 与后台界面产物存在。
token 只从环境变量读取（临时 `.npmrc`），不写入仓库任何文件。
发布后请同步更新 `plugin-catalog.json` 中的推荐版本。

## 18. 命名扩展点（本轮新增）

第 13 节里"插件能被扩展"的唯一通道是插槽（`ctx.slots.register`），且只覆盖站点渲染。
本节把它推广为**命名扩展点**：插件可以声明自己的挂载点（声明），别的插件向它贡献内容（贡献），
再由各作用域的宿主渲染或触发。概念与取舍见 [ADR-017](../adr/ADR-017-named-extension-points.md)。

### 18.1 三作用域与 payload 形状（务必看清）

内核只有**一套**注册表（`ExtensionRegistry`），三个作用域共用记录结构与裁决规则，
但 **payload 形状按作用域而异** —— 这是最容易写错的地方：

| 作用域 | 谁渲染 / 触发 | payload 形状 | 产物入口 |
| --- | --- | --- | --- |
| `render` | Core 渲染管线（模板 `slot()` helper） | `SlotComponent`（`{ name, render(context) }`） | `./dist/*.js`，默认导出 `{ name, render }` |
| `admin` | 后台 SPA 的 `<PluginSlot>` | **浏览器可 import 的 ESM 模块 URL 字符串** | `./admin/*.js`，默认导出贡献组件 |
| `server` | 提供方在自己的流程里 `ctx.extensions.apply()` | `ExtensionHookModule`（`{ apply(payload, ctx) }`） | `./dist/*.js`，默认（或具名）导出 `apply` |

- admin 作用域的 `payload` 由 Core 从 `entry` 换算成托管 URL（`/plugin-admin/<pluginId>/…`），插件不需要自己拼路径；
- 扩展点名形如 `<pluginId>.<area>[.<position>]`，段内允许驼峰（标准插槽已有 `post.beforeContent` /
  `post.afterContent`）；Core 预置的九个标准渲染插槽（第 13.1 节）视为已声明，贡献它们无需先声明；
- 贡献的 `mode` 缺省 `append`、`order` 缺省 `0`。

### 18.2 声明（提供方）——`manifest.json` 的 `extensionPoints[]`

```json
"extensionPoints": [
  {
    "name": "rice.posts.listActions",
    "scope": "admin",
    "replaceable": true,
    "description": "文章列表页右上角的操作区。",
    "props": [
      { "name": "kind", "description": "内容类型标识，固定为 'post'。" }
    ]
  }
]
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 是 | 扩展点名（全局唯一），如 `rice.posts.listActions` |
| `scope` | 是 | `admin` / `render` / `server` |
| `replaceable` | 否 | 是否允许**第三方**用 `replace` 接管（缺省 `true`）。提供方自己的 `replace` 不受它约束 |
| `description` | 否 | 面向使用者的说明 |
| `props` | 否 | 契约文档：告诉贡献者会收到哪些字段（admin 为组件 props 名，含名字与说明） |

声明只描述**契约**（名字、作用域、可替换性、会传什么），真正的挂载点由插件自己的界面或流程决定。
声明 `extensionPoints` **必须**同时声明能力 `extensions:declare`。

### 18.3 贡献（消费方）——`manifest.json` 的 `contributions[]`

```json
"contributions": [
  {
    "point": "rice.posts.editorBody",
    "scope": "admin",
    "mode": "replace",
    "order": 10,
    "entry": "./admin/editor.js",
    "style": "./admin/editor.css",
    "label": "Markdown 编辑器"
  }
]
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `point` | 是 | 扩展点名（必须是标准插槽或某个插件 `extensionPoints` 之一） |
| `scope` | 是 | 与扩展点一致；入口白名单随之变化 |
| `mode` | 否 | `append`（缺省，追加）或 `replace`（接管） |
| `order` | 否 | 排序权重（缺省 0）。append 时降序靠前；replace 时取最大者 |
| `entry` | 是 | admin 限 `./admin/*.js`；render / server 限 `./dist/*.js` |
| `style` | 否 | 仅 admin：随贡献加载的样式（引用计数注入 / 卸载） |
| `permission` | 否 | 仅 admin：按当前用户权限过滤（不满足则不下发） |
| `label` | 否 | 展示名 |

声明 `contributions` **必须**同时声明能力 `extensions:contribute`。贡献随插件启停自动生效与消失。

### 18.4 运行时门面 `ctx.extensions`

```ts
ctx.extensions.declare(point)                    // 声明扩展点（能力 extensions:declare）
ctx.extensions.contribute(point, payload, opts)  // 贡献（能力 extensions:contribute）
ctx.extensions.apply(point, payload, opts)       // 触发 server 作用域钩子（提供方用；无需额外能力）
ctx.extensions.list()                            // 诊断：全部扩展点摘要
```

- `contribute` 的 `opts`：`{ scope?, mode?, order? }`，`scope` 缺省 `render`；
- `apply` 的 `opts`：`{ onError?: 'abort' | 'skip' }`，缺省 **`abort`** —— 贡献抛错即上抛，
  避免把未经验证的数据写进库；`skip` 时记日志并沿用上一版 payload；
- `declare` / `contribute` 返回 `Dispose`，句柄由 Core 随插件停用回收。

与 `ctx.slots.register` 的关系：它是 **render 作用域贡献的别名**（历史 API，继续可用；
`priority` 映射为 `order`）。**读旧文档的人不用改代码**。

### 18.5 替换裁决规则

- **append**：按 `order` 降序返回全部（同序按注册顺序）；
- **replace**：默认内容与所有 append 贡献都不呈现，只取**胜出者**（`order` 最大；
  同分由 `pnpm validate` 阶段判错，运行期按 `consumerId` 字典序兜底并告警）；
- **提供方例外**：`replaceable: false` 约束的是**第三方**，**提供方自己的 `replace` 不受约束**。
  活样例：媒体库的 `rice.media.picker` 声明 `replaceable: false`，媒体库自己用 `mode: "replace"`
  贡献默认面板（见 `plugins/official/media/manifest.json`）。

### 18.6 命名、能力与校验

- 扩展点名：`^[a-z][A-Za-z0-9]*(?:[.-][A-Za-z0-9]+)+$`（如 `rice.posts.listActions`）；
- 能力：`extensions:declare` / `extensions:contribute`；`slots:register` 继续作为 render 贡献的别名能力；
- `pnpm validate` 的静态项：能力声明、扩展点全局唯一、贡献入口的作用域白名单与文件存在、
  `style` / `permission` 仅 admin、贡献指向的 `point` 必须已声明、同一扩展点上 `replace` 且 `order` 相同的冲突。

### 18.7 如何调试"为什么没生效"

**先看接口的过滤不对称（刻意设计）**：`GET /api/admin/extensions` 返回的 `points` 与 `contributions`
过滤口径不同 ——

- **`points`（扩展点声明）不按权限过滤**：声明是插件暴露的**静态能力信息**（名字、作用域、是否可替换、
  会传哪些字段），权限管的是"你能不能往这里贡献"，两者语义不同。若把声明也一起过滤，
  "贡献为什么没生效"就无法诊断 —— 你会看到"这个扩展点不存在"，而真实原因可能是插件没启动或你权限不足。
  （它仍只下发**提供方已启动**的扩展点，但这与"按查看者权限过滤"是两回事。）
- **`contributions`（贡献）按"启用态 + 权限"过滤**：贡献方插件未启动、或当前用户不具备其 `permission` 时，
  该条贡献不出现在返回里。

于是看一眼返回就能分辨现象与原因：

| 现象 | 结论 |
| --- | --- |
| 既无 point 也无 contribution | 扩展点不存在（提供方未启用 / 名字拼错） |
| 有 point、无 contribution | 提供方在，但贡献方未启动、你权限不足、或消费者未启用 |
| 两者都有 | 正常渲染 |

> **"贡献方插件未启动"与"权限不足"走的是同一处判据**（服务端对贡献逐条做启用态与权限判断），
> 因此两者可见现象完全一致 —— 都表现为消费者渲染默认内容。这是扩展点**可回退契约**的一部分
> （有贡献则接管、无贡献则回落默认内容），而不是两种不同的故障。
> 安全上也没有额外代价：该端点要求已登录的后台会话，且声明不含 payload 与任何数据。

其余按顺序排查：

1. **未声明的扩展点只告警不拒绝**：`point` 拼错时运行期只会看到一条 warn（插件启停顺序不确定，
   消费方可能先于提供方启动），不会报错 —— 先跑 `pnpm validate` 让拼写错误暴露；
2. **权限被过滤的贡献根本不下发**：admin 贡献声明了 `permission` 而当前用户不具备该权限时，
   `/api/admin/extensions` 里不会有它（超级管理员 `*` 全放行）；其可见现象与"贡献方未启动"一致（见上）；
3. **命令式贡献不会出现在后台**：admin 作用域只支持**声明式**贡献（命令式的 `ctx.extensions.contribute`
   没有浏览器可 import 的入口），Core 会跳过并留 debug 日志；
4. **插件未启动 = 贡献消失**：确认插件已启用且 `start()` 成功；
5. **贡献组件读不到 context**：多半是没在 `defineAdminContribution({ props: [...] })` 里声明字段 ——
   未声明的同名字段会落进 `ctx.attrs`，`setup(props)` 拿到 `undefined`（表现为"点了没反应且无报错"）。
   可显式声明 `props: ['value', 'onChange']`，或改从 `setup(props, ctx)` 的 `ctx.attrs` 读取；
6. **admin 界面不刷新**：改了 SDK 需 `pnpm --filter @ricenote/admin-sdk build`；
   插件界面资源是 `no-cache`，刷新即可。

### 18.8 现有锚点（跨插件锁死的契约）

官方的文章 / 页面编辑体验就是通过下面这批锚点协作的（提供方在 `rice.posts` / `rice.pages`，
消费方目前是 `rice.editor-enhance`）。**不要自创名字**：

| 锚点 | 作用域 | 可替换 | context（贡献者声明 props 时对齐） |
| --- | --- | --- | --- |
| `rice.posts.listActions` / `rice.pages.listActions` | admin | 是 | `kind`（`'post'` / `'page'`） |
| `rice.posts.editorToolbar` / `rice.pages.editorToolbar` | admin | 是 | `kind`、`value`、`onChange(next)`、`onPreview()` |
| `rice.posts.editorBody` / `rice.pages.editorBody` | admin | 是 | `kind`、`value`、`onChange(next)`、`onPreview()` |
| `rice.media.picker` | admin | 否（第三方） | `onPick({ url, fileName, mimeType, size })`，贡献权限 `media.manage` |

说明：

- `kind`：三个锚点都有，便于同一份贡献组件复用到文章与页面；
- `value` / `onChange(next)`：读写正文（Markdown）；`onPreview()` 触发服务端预览产出（`rice.posts.*`
  返回渲染并消毒后的 HTML `Promise<string>`，`rice.pages.*` 侧由编辑页负责展示）；
- `rice.media.picker`：媒体库启用时用完整面板替换消费者的默认内容；**未安装媒体库时消费者渲染默认内容
  = 一行直接填链接**，因此消费者必须给出降级路径。面板不带外层对话框与标题，容器由消费者提供。

## 19. 插件声明权限点（v0.5.4）

权限点的**展示文案与归属由拥有它的那一方声明**：插件写在自己的清单里，Core 写内核的控制面权限点。
Core 校验全局唯一并聚合成一份目录，`rice.authorization` 只负责按站点语言展示与分派
（决策与理由见 [ADR-018](../adr/ADR-018-plugin-permission-declarations.md)）。

> 因此**新增插件不需要改动 `rice.authorization`** —— 在旧版本里它的 `src/permissions.ts`
> 硬编码了所有插件的权限点，那正是这一版要消除的反向耦合。

### 19.1 声明方式

```json
"permissions": [
  {
    "key": "post.publish",
    "label": { "zh-CN": "发布与撤回文章", "en": "Publish and unpublish posts" },
    "group": { "zh-CN": "内容", "en": "Content" }
  }
]
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `key` | 是 | 权限点标识，`<域>.<动作>`（两段都允许短横线），例如 `post.publish`、`nav.manage` |
| `label` | 是 | 展示名（`localizedText`：字符串或多语言对象，见第 4 节） |
| `group` | 是 | 权限管理界面里的分组名（同样是 `localizedText`）。组名是自由文案，同一站点内保持一致即可 |

`key` 与插件 ID **不绑定**（`rice.posts` 声明 `post.*`）：域表达的是业务归属而不是包名。

### 19.2 两条规则（与启动期、`pnpm validate` 完全一致）

| 情况 | 处理 |
| --- | --- |
| 同一标识被两方声明（跨插件，或与 Core 的权限点冲突） | **错误**：`RN_MANIFEST_INVALID`，启动失败、`pnpm validate` 失败 |
| 某标识被使用但无人声明 | **仅告警**：启动日志与 `pnpm validate` 给出提示，插件仍照常工作 |
| `key` 不符合 `<域>.<动作>` 形式 | **错误** |

为什么"用了没声明"只告警：**鉴权按权限点标识字符串比对，与是否声明无关**
（`SecurityGateway` 只问 authorization 的 resolver）。声明影响的是**展示与归属**，
因此漏声明不该让站点起不来 —— 但它意味着权限目录里这个权限点没有中文名，
只会落在「未登记」分组，作者应当补上。

### 19.3 "使用"是怎么被看到的

Core 在三个位置登记使用点，合起来就是"谁在用它"：

| 来源 | 时机 | 说明 |
| --- | --- | --- |
| `manifest.admin.pages[].permission` | 加载期（静态） | 后台页面入口 |
| `manifest.contributions[].permission` | 加载期（静态） | admin 作用域的扩展点贡献 |
| `ctx.routes.adminApi({ permission })` / `ctx.adminMenu.add({ permission })` | 运行期（插件 `start()`） | 命令式注册 |

`pnpm validate` 只能看到前两项（运行期注册在 CLI 里不存在），因此第三项靠启动日志里的同一份告警兜住。

### 19.4 阅读聚合结果

`core.security@1` 的 `listDeclaredPermissions()` 返回 `DeclaredPermission[]`：

| 字段 | 说明 |
| --- | --- |
| `key` | 权限点标识 |
| `label` / `group` | 声明方提供的文案；**未声明时为 `null`**（界面回退为显示标识本身 / 「未登记」） |
| `declaredBy` | 声明者插件 ID；`null` 表示由 Core 声明 |
| `usedBy` | 实际使用该权限点的插件 ID（按字典序） |

权限目录因此天然支持三种项：**已声明且在用**、**已声明未用**（插件预留）、**未声明但在用**（待补声明）。

### 19.5 宿主版本要求

`permissions` 是 `0.5.4` 引入的 manifest 字段，而 manifest schema 设了 `additionalProperties: false`：
**旧宿主读到未知字段会直接判定清单非法**（装不上或启动失败）。因此：

- 声明 `permissions` 的插件，`peerDependencies` 里的**宿主区间必须写在 `^0.5.4` 及以上**；
- 官方插件的做法是**跟随宿主的次版本**，当前统一为 `^0.6.0`（见第 17.4 节的打包契约第 1 条）。

这是个**可选**字段：不声明即表示"本插件没有自有权限点"，不会因此被判非法。

### 19.6 声明之后：谁来授权

声明只让权限点**出现在目录里**，不会自动把它授予任何人：

- 内置角色自 `0.5.4` 起**只剩 `administrator`**（权限 `*`）。插件不再替站点决定"谁该有什么权限"，
  早期那种"随插件安装顺带授予 editor / author"的做法已随内置角色一起移除。
- 因此新插件的权限点默认**没有任何角色持有**，需要站点管理员在后台「角色与权限」页自建角色并分配。
- manifest 里**没有**、也不应有"把权限点授予某内置角色"的字段 —— 权限分派属于站点配置，不属于插件元数据。

面向插件作者的完整操作步骤见 wiki 的
[权限点声明与角色分配](https://github.com/ricenote/ricenote/blob/main/wiki/Plugin-API-Permissions.md)。
